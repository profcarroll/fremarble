Fremantle Calling

A 2009 Nokia N900 with 245 MB of RAM cannot run a language model. It can be the hand, the screen, the keyboard, the camera, and the radio for one running on my free Ampere node. Four ways to build that, ranked by how much I believe I can finish by December 9.

student: (me) · model: Claude Fable 5.1probed: 2026-09-07status: human play-tested

Decision after faculty feedback, 2026-09-07: proposal 2, Tilt Levels. It carries a real question (does the model design better levels by studying how they are played, and what do those levels look like?), runs offline from day one, and inherits the Marble Madness vocabulary as a design language for the prompt. From proposal 1 it borrows the autonomy trick: tilt comes from one input source that can be the accelerometer or a named pipe, so a bot driven over SSH can play every level pack headlessly while a human operator plays the real thing. The gap between bot telemetry and human telemetry is part of the finding.

Model plan: the level designer is qwen3-coder:30b-a3b on sld-cloud in overnight batch (the self-hosted outcome, and the thing under study). Gemini Pro drafts the pygame client and the tilt harness; Copilot covers editor completion, commit messages and PR review; Claude is rationed to direction, bootstrap and harness files, and hard debugging. Each commit's trailer names the model that wrote it.

Plan changes: milestone zero shrinks to an scp of a JSON level pack over the legacy SSH shim; the live relay and firewall decision wait until telemetry upload needs them. The on-device pygame frame-rate test moves to the first week, because a failing number sends the client to proposal 4's C toolchain before the midterm pitch.

The one finding that shapes every idea. The N900 can reach the node, but its 2009 OpenSSH cannot finish a handshake with a 2024 sshd (no hostkey alg). So the tunnel the Week 11 kit assumes does not exist yet for this device. Whatever I build, milestone zero is a bridge: either a narrow HTTP relay on the node with a shared token and one more firewall rule, or a legacy-algorithm exception on the node's sshd. Both are a real security decision to argue in the proposal, not a footnote.

Four proposals, ranked

The question I was asked to settle: a game on the N900, a native app that uses a free self-hosted model, or both. My read after the probe is that "both" is not a stretch goal, it is the natural shape: the node is slow enough that reading-speed text is the honest interface, and reading-speed text is what a text game wants anyway.

Dungeon Master in the Cloud

gamenative appboth

A text-and-tiles adventure on the N900. The device draws rooms, inventory, and the map in pygame at 800×480; the narrator and every non-player character are the model on the node. Tokens stream onto the screen at 6 to 10 per second, which on a handheld reads as a game "typing," not as lag. The world state stays on the device as a small JSON document, so the model never has to remember anything: each turn the game sends state plus the player's line and gets back narration plus a state diff.

Why it is viable

  • python2.5 + pygame 1.9.1 are in the archival catalogue; both install to /opt, not the 89 MB root.
  • qwen3.5:4b at reading speed is enough; the 30B coder is for writing the code, not running the game.
  • Game logic runs offline; only narration needs the network, so the game degrades to canned text when the node is away.

Where it will hurt

  • Milestone zero, the bridge, before anything is playable.
  • Python 2.5 has no json module; the model will keep writing 2026 Python. That is the drift lesson in miniature, and my bootstrap file has to pin it.
  • Keeping the model inside a state schema at 4B parameters needs a harness and a test set (Week 9 material).
Question for faculty: is a game whose "engine" is a remote model still a small-device project in your reading of the brief, or does the device need to carry more of the work?

Tilt Levels

gamenative apptelemetry

A marble-tilt game driven by the N900's accelerometer, which I confirmed is readable from a file in sysfs with no driver work. The model on the node is not in the play loop at all. It is the level designer: it emits levels as JSON, the device caches a pack of them, and after each session the game uploads play telemetry (time per level, deaths, where the marble stalls) and asks the model for a tuned next pack. This is the ETK method from Week 5 applied to game difficulty: measure, feed back, tune, on an underpowered box.

Why it is viable

  • Fully playable offline from day one; the model only ever improves it.
  • pygame plus one sysfs read; the maemo catalogue already ships three accelerometer toys as proof.
  • The telemetry design is the assignment for Week 9 anyway.

Where it will hurt

  • Physics on a 600 MHz Cortex-A8 in Python: frame rate is a real budget and I will have to measure it.
  • Level JSON from a 4B model will need a validator that rejects unplayable maps, or a bigger model on a batch schedule.
Question for faculty: does "the model designs, the device plays" satisfy the self-hosted AI outcome, given the model is never called while someone is holding the device?

Radio Oracle

native apphardwareadvanced modalities

A Hildon app that turns the N900 into a talking, broadcasting assistant. Type a question on the hardware keyboard, the node answers, espeak (in the catalogue) reads it aloud on the device, and the N900's built-in FM transmitter carries the voice to any nearby car or kitchen radio with the first line of the answer scrolling as RDS radio text. Stretch: point the camera at something, send the frame to gemma4:e4b, and have the radio describe what it sees.

Why it is viable

  • Every piece is on the device already: FM transmitter exposes power, frequency and rds_radio_text as sysfs files; camera is /dev/video0; espeak 1.46 installs from the catalogue.
  • A demo that a room full of people hears on a radio is a strong final showcase.

Where it will hurt

  • Vision on a CPU-only node is slow: prompt evaluation of an image at rung 2 needs measuring before I promise it.
  • RDS text is 64 characters and the transmitter is short range and regulated; scope stays "in the room."
  • Less "game," more "instrument." Probably my choice if faculty steer away from games.
Question for faculty: is a broadcast demo acceptable in Room 720, or should I plan on a wired line-out for the showcase?

Cloud-Built, Hand-Run

gametoolchainETK pattern

The purest version of the Week 5 case study: write a small C game with SDL 1.2 and the SGX OpenGL ES path, cross-compile it on sld-cloud with the arm-linux-gnueabi toolchain, package it as a gzip-only .deb, and install it on the N900 through my own laptop-hosted catalogue from the software guide. No model at runtime; the model is the co-author of every line of C and the whole build pipeline. Most ambitious on the systems side, least ambitious on the AI side.

Why it is viable

  • Cross compiler is in Ubuntu's repo; the packaging gotchas (xz vs gzip, unsigned repo) are already documented in this course's own guide.
  • SDL 1.2, SDL_gfx, SDL_mixer and GLES headers are all in the catalogue.

Where it will hurt

  • glibc mismatch: gcc 13 targets a much newer libc than Maemo's. I need a sysroot copied off the device, or static linking, or fall back to tcc on the handheld itself.
  • Hard to show the "large language model" half at the showcase beyond the commit history.
Question for faculty: would you rather see this as the build system underneath proposal 1 or 2, instead of a project on its own?

The bytes-to-atoms rule. Assistants in this project emit bytes; only I move anything onto the device. Copilot is not granted tools: I paste the bootstrap and task into its prompt, it prints each file behind a header, I split the output, read it, carry it over the legacy SSH shim, and run it on the N900's own interpreter. Whatever happens on the handheld afterward is mine. The same rule is the game's architecture: the level designer on the node emits a text file, which is data and never code, gated by the validator, then by bot play, then by the human operator.

First human play-test

The instructor played the same level on the device, real accelerometer, two-minute limit. The verdict from the hand: very tricky, the input physics need tuning, maybe haptics, a more naturalistic feel. The telemetry says the same thing in numbers.

Bot, run 4Human, run 1
Outcomegoaltimeout

Deaths07, three of them within 1.6 s of each other

Time in the first corridor3 s85 s, the last 40 parked in a corner with the device nearly flat

What the trace says the physics are doing wrong. The gain was tuned for a file that writes a steady 600 mg; a hand does not do that. At the current gain a full tilt accelerates the marble at about 21,000 px/s², thirty times faster than a marble on a tilted table would move at this scale, and terminal speed is well past a screen-width per tenth of a second. Physics run per frame, and the frame rate wandered between 82 and 124, so the same tilt does different things at different moments. There is no dead zone, so a device resting almost flat (18, −36 mg in the last forty seconds) still pushes the marble into a corner. Walls return 60 % of the speed, which is why the human's trace is a ping-pong record. And a hole kills on touch, which is why the bot died hugging a wall and why three human deaths came in under two seconds: respawn, rush, die.

This is the first bot-versus-human gap in the study, and it is the one the plan predicted: a level and a physics model that a scripted bot clears trivially can be nearly unplayable by a person. The fix goes to the drafter as a tuning spec with these numbers attached; the level designer on the node never sees a "good" level until a human can finish one.

My recommendation

Proposal 1, with proposal 4's toolchain held in reserve if Python on the device turns out too slow to draw. It is the only one of the four that is a game, a native app, and a live use of the self-hosted model at the same time, and its failure modes are all things the course teaches: drift toward modern Python, a small model wandering off a schema, a slow box that has to be measured rather than trusted.
